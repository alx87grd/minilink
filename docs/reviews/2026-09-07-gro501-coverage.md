## 1. Complexity review

### Not over-complexified (no action)

- **`analysis/linear.py`** — matrices in, arrays out, 332 lines, no ports and
  no plotting. The two-tier split (`linear` = matrices, `frequency` /
  `time_response` = systems) is the right cut and both docstrings state it.
- **`graphical/control/`** — a 76-line figure spec plus two ~160-line
  backends. 490 lines buys matplotlib *and* plotly from one description;
  the Colab requirement pays for it.
- **`Error` vs `Sum`** — 25 lines for a named comparison block. Diagrams read
  better.
- **`Demux` port ids** (`y[0]`, `y[1]`) — strictly better than `out0`.

### Over-complexified (four findings)

**C1 — `@` carries three semantics.** `composition.closed_loop` dispatches on
operand type: a non-`System` right operand goes to `feedback()` (`L @ 1`,
`L @ K`); an error-driven controller goes to `feedback(series(C, G))`;
anything else falls into the pre-existing ~500-line declaration/qdq
machinery. Layered on top: `PROFILE_PORTS` (8 rows, 5 of them identical
`("y", "r", "u")` differing only in `plot_space`), the `ports=` layout switch
on classical blocks, and `error_input()` fallback rules. One operator, three
meanings, two registries.

Mitigating: only the first two paths fire on a classical-control course, so
the cost lands on the maintainer, not on students. Note that
`_is_controller_like` now also fires on any block with an `e` input — that
heuristic widened, and it drives `autowire` for every diagram.

**C2 — `facades.py` restates 13 signatures by hand.** Each analysis method
repeats `(x_bar, u_bar, t, params, *, of, wrt, …, method, eps)` verbatim and
forwards; ~400 lines of the file's 1 228. Every future keyword needs two
edits. It has already drifted: `time_response.step_response` documents "five
times the slowest stable time constant" while `linear.settling_horizon`
returns `8.0 / σ_min`.

**C3 — `TransferFunction(ports=…)` does port surgery.** `LTISystem.__init__`
builds the ports, then the subclass clears `self.inputs` / `self.outputs` and
re-adds them. The result is consistent (checked), but it is build-then-
demolish, and `ports` now accepts four values (`None`, `"plant"`, `"error"`,
`"reference"`).

**C4 — one `PID` class for P / PI / PD / PID reports poles that do not
exist.** The block always carries `2n` states whatever the gains, so a zeroed
gain leaves an unobservable mode in every linearization:

```
PID(Kp=20, Ki=0, Kd=0) >> Pendulum()          # a pure proportional loop

loop-gain poles: [-0.125 ± 2.211j,  0,  -20]   # should be the 2 plant poles
loop-gain zeros: [ 0, -20]                     # two exact cancellations
loop  H(s):  (10 s² + 200 s) / (s⁴ + 20.25 s³ + 9.905 s² + 98.1 s)
closed-loop poles: [-20, -0.125 ± 3.859j,  0]  # a pole on the imaginary axis
```

`analysis` has no `minreal`, so nothing cancels the pair. A student reading
`eigvals(A)` sees marginal stability that is not there, and a hand-traced root
locus does not match the drawn one. This is the finding with teaching
consequences: guide exercises §9.6 and §9.7 are exactly these loops.

**Minor** — `root_locus` refines to 1 114 points / 1.9 s on a 4-state system;
`_refine_jumps` roughly triples the requested `n = 400`.

## 2. GRO501 coverage

position loops to the Table 2 specs, implemented as difference equations on
an Arduino. APP4 (§1.3–1.4): bicycle-model MIMO plant, LQR on a stated cost,
nested loops for the parking mode, pole placement to a prescribed set, and a

The Table 2 loop-shaping specs are already computable through the
internal-wire selector, undocumented for this use:

```python
T = C @ G
T.bode(of="error:e", wrt="r")   # S(jw) — disturbance sensitivity
T.bode(of="ctl:u",   wrt="r")   # CS(jw) — measurement noise to command
```

Checked `|S| + |T| = 1` at ω = 1. An *input* disturbance still needs a
hand-wired `Sum`, and there is no named verb.

## 3. Verdict

Roughly four-fifths of GRO501 runs on `dev-fable` today. The frequency-domain
half — the part this branch was built for — is there and reads well. What is
missing is the APP4 state-space design half (observer, pole placement) plus
the z-domain; those are three self-contained additions, not architecture
work. G3 comes first: it is a small change and it is the one place where the
tool currently disagrees with the course's own exercise set.

## 4. Second pass — solidifying the continuous module

Follow-up sweep the same day, running the guide's own §9.6 / §9.7 / §9.10
exercise systems through every verb. Three more defects, all now fixed on
`dev-fable`.

**F1 (major) — `margins()` reported `inf` whenever the gain crossover fell
outside the automatic frequency band.** `frequency_range` built the band from
the poles and zeros, dropping any root at the origin (no rate) and never
looking at the magnitude. Two common shapes missed the crossover entirely:

| loop | reported | true |
| --- | --- | --- |
| `10 / (s(s+10))` — any PI or I loop | `PM = inf` | `PM = 84.3°` at ω = 0.995 (band started at ω = 1) |
| `1000 / (s+1)` — large static gain | `PM = inf` | `PM = 90.1°` at ω = 1000 (band ended at ω = 10) |

Infinite margin is the most dangerous wrong answer a margin tool can give —
it reads as "unconditionally safe". It also truncated the Bode and Nyquist
plots, which share the band: a PI loop was drawn with none of its integrator
slope. `frequency_range` now widens the band until it brackets `|G| = 1`,
down while the magnitude is still climbing steeply (an integrator gains a
decade per decade) and up while it is above one, bounded at eight decades
each way. A flat low-frequency gain stops the walk immediately, so
well-scaled systems keep their tidy decade bands.

**F2 (moderate) — `PID.f` and `PID.ctl` disagreed about `tau`.** `ctl` clipped
the filter constant to `max(tau, 1e-3)` and `f` used it raw, so with
`tau = 1e-6` the state rate ran a filter a thousand times faster than the one
the command was computed from. The block was internally inconsistent, and
every linearization through it was wrong. `tau > 0` is now validated at
construction and neither method clips.

**F4 (minor) — `closed_loop_poles` divided by zero** at `K = -1/d` on a
channel with feedthrough, raising `LinAlgError` out of a `RuntimeWarning`.
Now returns infinite poles, which is the answer.

**Checked and found correct** (no action): `step_info` against an analytic
second-order system (overshoot 16.336 % vs 16.303 % exact, peak time 3.623 s
vs 3.628 s, settling 8.08 s); the gain margin on `1/((s+1)(s+2)(s+3))`
(35.56 dB → `K* = 60.0`, exact); the marginal loop `1/(s(s²+s+1))`
(`GM = PM = 0` at ω = 1, exact); `dof > 1` PID; `ProportionalController` in
compensator form; every `plot_` verb on an integrator loop.

**Left as maintainer decisions** (not defects):

- `step_info` on a divergent response returns `nan` for steady state and
  settling time and a meaningless rise time. Honest, but a student tuning an
  unstable loop gets no signal that the response diverged.
- `feedback()` silently takes component 0 when a scalar loop closes on a
  vector output ("the standard choice: the first component"). Convenient for
  `y = [θ, θ̇]`, a trap for a plant whose first output is not the regulated
  one. A warning, or requiring `of=` for vector outputs, would be safer.
